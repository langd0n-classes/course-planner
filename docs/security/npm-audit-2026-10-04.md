# npm dependency security assessment — 2026-10-04

Review of [issue #23](https://github.com/langd0n-classes/course-planner/issues/23) against baseline commit `e6e283a` on `fix/23-npm-audit`.

## Result

The baseline has production-reachable Next.js request-handling vulnerabilities, including Server Action denial of service and proxy bypass surfaces. Upgrade before deploying this baseline. API ownership checks reduce the impact of proxy bypass but do not protect the framework action decoder. This satisfies the issue's condition for treating production exposure as blocking rather than assuming all findings are development-only.

| Audit | Low | Moderate | High | Critical | Total affected packages |
| --- | ---: | ---: | ---: | ---: | ---: |
| Historical issue count | 1 | 5 | 11 | 1 | 18 |
| Clean baseline, full dependency tree | 1 | 5 | 22 | 4 | 32 |

These are npm's affected-package counts, not unique advisories. The baseline contains 104 unique GHSA identifiers. Nine retained package entries represent three underlying advisories; none has an identified exploitable path in the checked application/workflows. `--omit=dev` still includes Prisma CLI/configuration through `@prisma/client`'s optional Prisma peer; package placement alone is not proof of production execution.

Reachability below is a source/configuration assessment, not a live exploitation test. “Production surface” and “conditional” conservatively include framework endpoints whose exploit prerequisites depend on inputs or hosting behavior not established here. “Not reached” means the advisory's vulnerable operation or required input is absent from the checked configuration; it is not a guarantee for future configuration changes. Development includes tests, lint, CLI setup, and builds.

Vitest 4.1.11 itself requires `es-module-lexer` 2.x and `std-env` 4.x, upgrading those transitives from major 1 and 3 respectively. These are upstream-supported requirements of the smallest patched Vitest minor, not manual compatibility overrides. Framework minor, native codec, and test-runner changes carry more regression risk than ordinary patch updates; validation is recorded below.

The app has no `next/og` ImageResponse call, so that path is not reached; selecting the patched release avoids introducing a known critical finding.

The test configuration caps Vitest at four workers and sets a 15-second per-test timeout. With the default worker count, six existing UI tests timed out under load; the 150-Topic test also exceeded the default five-second timeout when run alone. All tests pass with the configured limits. The updated Next lint configuration reports existing patterns in seven React effects, one function ordering, and two `module` variables as errors. `eslint.config.mjs` keeps those three rules enabled as warnings; lint completes with zero errors and 34 warnings.

## Retained findings

- **Braces recursion, GHSA-vfj7-8cjw-p6xm:** no patched release was available (`braces` latest is 3.0.3). Five npm entries are `braces`, `micromatch`, `fast-glob`, `@next/eslint-plugin-next`, and `eslint-config-next`. The checked lint configuration supplies no attacker-controlled or deeply nested glob. Revisit when the upstream parser is patched or lint inputs change. Downgrading the framework lint configuration to 14.x is not a safe fix for this Next 16 app.
- **Deepmerge recursion, GHSA-ggr8-5vv4-36mx:** fixed in 8.x, outside Prisma 6's supported range. No cyclic object configuration or request-to-config merge exists here. Forcing a new major into Prisma or downgrading Prisma to 6.12.0 adds compatibility risk without removing an active application exposure.
- **Effect request-context contamination, GHSA-38f7-945m-qr2g:** fixed in 3.20.0, while Prisma config pins 3.18.4. No request-scoped Effect fibers/RPC are used by the app. Keep the supported Prisma dependency graph; revisit with an upstream compatible config release or before adding Effect request handling. These two advisories propagate to `@prisma/config` and `prisma`, producing the other four npm entries.

Prisma runs during client generation and production deployment migrations (`scripts/vercel-build.sh`), so “tooling” includes the build/deploy environment. The reachability conclusion relies on its trusted local configuration and absence of request handling, not on the CLI being absent from an install.
